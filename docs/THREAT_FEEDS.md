# Threat Feed Integrations

Averrow ingests threat intelligence from ~54 external feeds split across three categories: **ingest feeds** (40) that create new threat records (three of these — CISA KEV, NVD CVE, and EPSS — write aggregated insight digests to `agent_outputs` instead, see below), **social feeds** (4) that populate `social_mentions`, and **enrichment feeds** (10) that annotate existing threats. This document covers the feed architecture, individual feed integrations, and operational patterns.

## Source Files

- **Feed modules:** `packages/averrow-worker/src/feeds/`
- **Feed runner:** `packages/averrow-worker/src/lib/feedRunner.ts`
- **Feed types:** `packages/averrow-worker/src/feeds/types.ts`
- **Feed handlers (API):** `packages/averrow-worker/src/handlers/feeds.ts`
- **Legacy adapters:** `packages/averrow-worker/src/threat-feeds.ts`
- **Scoring logic:** `packages/averrow-worker/src/lib/threatScoring.ts`

## Feed Module Interface

Every feed implements the `FeedModule` interface defined in `packages/averrow-worker/src/feeds/types.ts`:

```typescript
interface FeedModule {
  ingest(ctx: FeedContext): Promise<FeedResult>;
}

interface FeedContext {
  env: Env;
  feedName: string;
  feedUrl: string;
}

interface FeedResult {
  itemsFetched: number;
  itemsNew: number;
  itemsDuplicate: number;
  itemsError: number;
}
```

## Feed Ingestion Pipeline

### Execution Flow

1. **Cron trigger** — Ingest, social, and enrichment feeds run from the hourly orchestrator tick (`7 * * * *`) inside `runThreatFeedScan()`. The `*/5 * * * *` Navigator cron does not ingest feeds — it only owns DNS resolution, cube refresh, and KV cache warming. See `CLAUDE.md §6` for the full agent mesh schedule.
2. **Feed selection** — `runAllFeeds()` reads `feed_configs` from D1 to determine which feeds are due based on their configured interval
3. **Per-feed execution** — Each feed module's `ingest()` function is called
4. **IOC deduplication** — Before inserting a threat, the runner checks KV (`dedup:{type}:{value}`) with 24-hour TTL
5. **Threat insertion** — New threats are inserted via `INSERT OR IGNORE` for database-level dedup
6. **Brand matching** — Rule-based brand detection runs on each new threat
7. **Scoring** — Confidence scores and severity are calculated via heuristics in `packages/averrow-worker/src/lib/threatScoring.ts`
8. **History logging** — Results recorded in `feed_pull_history`
9. **Status update** — `feed_status` updated with health information

### IOC Deduplication

Two-layer deduplication prevents duplicate threat records:

1. **KV cache** — `dedup:{iocType}:{iocValue}` keys with 24-hour TTL for fast lookups
2. **Database** — `INSERT OR IGNORE` on the `threats` table using deterministic IDs generated by `threatId()`:

```typescript
function threatId(source: string, iocType: string, iocValue: string): string {
  // Deterministic hash from source + IOC type + IOC value
  return `thr-${source}-${hash}`;
}
```

#### Bulk insert path (list feeds) — `bulkInsertThreats`

The DB layer (deterministic PK + `INSERT OR IGNORE`) is **authoritative**;
the KV layer is only a fast pre-check. Large plain-list feeds should skip
the KV pre-check entirely and use `bulkInsertThreats(db, rows, chunkSize=50)`
(`lib/feedRunner.ts`), which flushes chunked `db.batch(INSERT OR IGNORE)`
transactions. This replaces the per-row
`isDuplicate`(KV GET)→`insertThreat`(D1)→`markSeen`(KV PUT) loop — 3
sequential round-trips per IOC — that got the worker reaped on large or
cold-cache pulls (e.g. `scam_blocklist` at 5k domains × 3 = 15k
subrequests). For N rows it is `ceil(N/50)` round-trips instead of `3N`,
and there is no cold-cache cliff (the DB always knows what exists).
`bulkInsertThreats` shares `insertThreat`'s exact column list + scoring via
one internal statement builder, so the single-row and bulk paths can't
diverge. **Routing through the shared `bulkInsertThreats` helper:**
`scam_blocklist`, `phishing_database`, `openphish`, `ipsum`, `urlhaus`,
`threatfox`, `feodo`, `tweetfeed`, `nrd_hagezi` (its brand-matched
typosquat rows: the domain × brand match runs in memory through a needle
index, one row per distinct domain, first brand wins — then one bulk flush
per 20K-new-domain chunk; a busy NRD day with thousands of matches was
thousands of serial KV+D1 round-trips).
**Already on a chunked `db.batch`
pattern via their own inline builders** (candidates to consolidate onto the
shared helper): `phishdestroy.ts`, `spamhausDrop.ts`, `blocklistde.ts`,
`cins_army.ts`, `dataplane.ts`, `emergingThreats.ts`, `torExitNodes.ts`,
`disposableEmail.ts`.

**Intentionally NOT bulk-migrated** (kept on the per-row path for a
reason): `dshield` / `sslbl` do a per-row `SELECT` + conditional `UPDATE`
to *enrich* existing threats (bulk insert would lose that, and both pull
≤100 rows so there's no reap risk); `otx_alienvault` also writes
`threat_actors` / `threat_attributions`; `typosquat_scanner` is an internal generator, not
a list fetch; `certstream` carries CT cert columns + a paired Durable
Object. Disabled/dead feeds (`phishtank`, `phishstats`, `cryptoscamdb`,
`talos_ips`, `urlscanio`, `digitalside_osint`) are skipped.

> **Cross-feed note:** the KV dedup key (`dedup:{iocType}:{iocValue}`) is
> NOT feed-scoped, so the old per-row path let one feed's `markSeen`
> suppress *another* feed's distinct (feed-scoped) row for the same
> domain. Dropping the KV pre-check restores per-source corroboration —
> a domain on two feeds now records one row per feed. Expect a one-time
> step-up in threats-per-domain counts for overlapping IOCs after a feed
> migrates. The outbound direction changes too: a migrated feed no longer
> *writes* `dedup:*` keys either, so e.g. `nrd_hagezi` no longer sets
> `dedup:domain:*` and `ct_logs` (`feeds/certstream.ts`, which still checks
> those keys) will now add its own `ct_logs` row (with cert columns) for a
> domain `nrd_hagezi` already inserted the same day, bumping
> `brands.threat_count` once per source — consistent with one row per source.

### Threat Classification

Each ingested threat is classified into one of these types:

- `phishing` — Phishing pages targeting brands
- `typosquatting` — Lookalike domain registrations
- `impersonation` — Brand impersonation sites
- `malware_distribution` — Malware hosting/distribution
- `credential_harvesting` — Credential theft pages
- `c2` — Command and control infrastructure
- `scanning` — Malicious network scanning
- `malicious_ip` — Known malicious IP addresses
- `botnet` — Botnet infrastructure
- `malicious_ssl` — Suspicious SSL certificates

## Feed Registry

All feeds are registered in `packages/averrow-worker/src/feeds/index.ts` into one of three maps: `feedModules` (ingest — 40 entries), `socialModules` (4 entries), or `enrichmentModules` (10 entries). The `feed_name` key must match the `feed_configs.feed_name` column.

**Cadence:** every ingest/social feed and 7 of the 10 enrichment feeds run inside the hourly orchestrator tick (`7 * * * *` in `wrangler.toml`) via `runAllFeeds` / `runAllSocialFeeds` / `runAllEnrichmentFeeds` — each feed's actual per-tick eligibility is decided by `shouldRunNow` (`lib/feedRunner.ts:940`), not by a per-feed cron trigger in `wrangler.toml`. That check is: skip while `feed_status.next_retry_at` is still in the future (the circuit breaker, see `CLAUDE.md §6`); otherwise run when the elapsed time since `feed_status.last_successful_pull` has reached the interval `parseCronIntervalMs` derives from that feed's own `feed_configs.schedule_cron` string, less a 60 s tolerance for cron trigger jitter. A feed with no `feed_status` row, or none with a successful pull yet, always runs. Three enrichment feeds are the exception: **GreyNoise** (`19 */4 * * *`, every 4h), **SecLookup** (`21 * * * *`, hourly), and **Pulsedive** (`27 */4 * * *`, every 4h) run on dedicated crons (`DEDICATED_ENRICHMENT_FEEDS` in `lib/feedRunner.ts`, skipped by `runAllEnrichmentFeeds` inside the orchestrator tick) because their per-IOC rate-limit sleeps would starve the shared enrichment chain — see `CLAUDE.md §6` for the full rationale and cron table.

> **What `nrd_domains` stores (D1 write cut, owner decision 2026-10-05).** `storeNrdReference` (`lib/nrd-store.ts`, re-exported by `nrd_hagezi.ts`) inserts only the new NRDs that equal a `lookalike_domains.domain` or `phantom_domains.domain`, with the filter IN the statement (`NRD_INSERT_SQL`: `INSERT OR IGNORE … SELECT j.value, ? FROM json_each(?) j WHERE EXISTS (… l.domain = j.value) OR EXISTS (… p.domain = j.value)`) — the matchers' own join predicate (`lib/lookalike-nrd-matcher.ts` `l.domain = n.domain`, `lib/phantom-matcher.ts` `t.domain = p.domain`), so it cannot drift from them. A handful of rows a day instead of ~443K (which cost ~1.3M row-writes/day plus as many again to purge). Still 2 binds and ≤1000 domains per statement; each new domain costs ~2 covering-index probes (`idx_lookalike_domain`, then `idx_phantom_domain` on a miss) ≈ 0.9M row-reads/day. Brand-keyword matching into `threats` and the R2 archive still cover EVERY new domain. The `nrd_hagezi_diffed` log reports `newTotal`, `archived`, `storedInD1` (rows actually inserted, from `meta.changes`), `deferred`, `matches`, `demotedKeywords`; `FeedResult.itemsNew` counts brand-match threats inserted, not NRDs.

> **Brand-keyword matching = combosquats only (`lib/nrd-brand-match.ts`, redesigned 2026-10-06).** Exact dnstwist typosquats are already claimed precisely by `nrd_domains` + `lib/lookalike-nrd-matcher.ts`, so this pass exists for brand-in-label domains that permutation tables don't contain (`paypal-secure-login.com`, `coinbasevalidate.com`, `micros0ft-support.net`, `att-login.com`). The old pass (brand NAME as a substring anywhere in the domain, + homoglyphs) wrote **43,010** threats on the first full Hagezi day — "line" in `006zhiboonline.com.cn`, "one" in `101graystone.com`, "nic" in `…clinic.com`, "intel" in `…intelligence.net` — which inflated brand counters/cubes and flooded the GSB/DBL/SURBL/seclookup/VT/pdns enrichment backlogs. Rules now:
> - **Keywords** per brand (`buildBrandKeywords`): the display name with non-alphanumerics removed; the name's words hyphen-joined (≥2 words of ≥2 chars, so `standard-chartered-login` matches); the canonical domain's registrable label only when the canonical has no subdomain/path AND the label is distinctive (`zellepay`, not `revenue` from revenue.ie or `apple` from tv.apple.com). Dropped: <3 chars, and `NEVER_KEYWORDS` (www, mail, cloud, web, online, app, dns, cdn, media, …) — infrastructure words that are lure vocabulary themselves.
> - **Classification** (`isGenericKeyword`): GENERIC = ≤4 chars, or in the curated `GENERIC_KEYWORDS` stop-list (96 dictionary words that are monitored-brand keywords today: line, booking, apple, amazon, office, intel, revenue, europa, fidelity, …), or itself a STRONG/WEAK vocabulary word; otherwise DISTINCTIVE. No embedded dictionary.
> - **Needles** (`keywordNeedles`): a DISTINCTIVE keyword plus all its single-character homoglyph variants (l↔1/i, o→0, a→4/@, e→3, s→5/$). A GENERIC keyword itself (generic rule), plus — if ≥5 chars — its digit/symbol-only variants (no l↔i letter swap) matched as DISTINCTIVE: a digit-swapped dictionary word (`amaz0n`, `app1e`, `0utlook`, `dr0pbox`) is itself the signal. Such a variant must not touch another digit (`merak123.world` is not `meraki`).
> - **Matching**: the domain's registrable part (public suffix dropped, incl. ccSLDs like `co.uk`) is split into segments on `-` and `.`. A needle occurrence counts only if the rest of its segment(s) is entirely vocabulary words and digit runs.
>   - DISTINCTIVE: STRONG or WEAK words — `paypal.to`, `coinbase66.com`, `mygoogle.me`, `githubcom.com`, `docsharepoint.top` match; `canvashouse.uk`, `3828betonline.com`, `bahiahondastatepark.com` don't.
>   - GENERIC: STRONG or GLUE words in the keyword's segment, AND a STRONG word either in that segment or in the nearest non-GLUE segment on either side (GLUE-only segments — `com`, `www`, `id`, `prime`, digits — are transparent). `att-login.com`, `dhlpayment.net`, `att.com-login.net`, `apple-id-verify.com`, `appleid-verify.com`, `myamazon-account.com`, `amazon-prime-login.com`, `dhl-parcel-redelivery.com` match; `line-store.com`, `onlineline.hair`, `amazonpay.com`, `apple-farm-login.com` don't.
>   - STRONG = phishing / parcel-smishing action words (login, signin, verify, secure, account, auth, password, reset, wallet, refund, billing, invoice, payment, support, helpdesk, kyc, 2fa, update, alert, tracking, parcel, delivery, redelivery, shipment, customs, …; `toll` and `package` deliberately left out — TollBit, software packages). WEAK = neutral glue next to a distinctive needle (my, the, www, com, official, app, web, portal, help, service, customer, pay, bank, mail, store, shop, doc/docs/drive/file/share/office/cloud, …). GLUE = the WEAK subset also allowed next to a generic keyword: my, id, pay, prime, www, com.
> - **Winner (order-independent)**: the longest qualifying needle (`amazonaws-login` → Amazonaws, `*-myshopify-com.store` → Myshopify), then the lowest brand id — brands are loaded `ORDER BY b.id` and `buildBrandKeywords` sorts by id again, so attribution never depends on D1 row order (verified: 0 winner changes across 5 shuffles of the 817 rows on a 443K day). A brand never matches its own canonical domain; another brand may.
> - **Runtime backstop (measured hit-rate rule)**: a BRAND that yields `NRD_KEYWORD_DEMOTE_AFTER` (100) rows through distinctive needles in one run has all its keyword texts demoted for the rest of that run — for every brand sharing the text. Demoted keywords AND their homoglyph variants still match, but only under the generic rule (a STRONG word required). Logged as `nrd_hagezi_keywords_demoted` (add those to `GENERIC_KEYWORDS`). Deterministic: the diff is processed in byte-sorted order and the count carries across flushes, so a retry demotes at the same domain. The busiest brand on a measured day had ~30 rows; on the whole 7-day window (3.1M) only `icloud`/`whatsapp` cross 100.
> - Unchanged: one row per domain, same `ThreatRow` (`typosquatting`, medium, confidence 60).
>
> Measured on the real list (817 monitored brands → 780 with a usable keyword; 210 generic / 747 distinctive keywords): two independent 443K-domain day samples went from 51,564 to **318** and **315** hits/day; ~2.3 s per day in the Worker code path (15 s for the full 3.1M window → 2,081). Of those, 14–24/day win via the generic rule and 0–1/day via a digit-swapped dictionary word; adding `com` as glue recovered `githubcom.com`/`robloxcom.com`/`paypalcom.com`-style squats. Manual read of a random 50 across both days: ~35 plausibly malicious/brand-abuse (numeric-prefix `953441coinbase.com`, `accountsoffice-logins.com`, `my-secure38-office.live`, `donotreply-google.com`, `voting-arbitrum.xyz`, `sharefile.uk`, `rabobank.si`, `soportesgffee-zendesk.help`, a `*-whatsapp.com` fake-download cluster, a bulk `<brand>.si` TLD-swap registrant), ~9 ambiguous, ~6 likely legitimate (`harvard2027.com`, `huawei.spb.ru`, `naoya-honda-officialwebsite.com`, `livetracking.com.br`). Known recall gaps by design: a brand glued to an arbitrary non-lure word (`googlemapsboost.com`, `tiktokfin.com`); known generic-rule FPs where a lure word forms a phrase with a dictionary brand (`secureshell.in`, `sentrytracking.com`). Existing rows written by the old matcher are untouched (cleanup is an owner decision).

> **Archive back-check (`lib/nrd-archive-backcheck.ts`).** Matchability is decided at ingest, so a lookalike permutation or phantom created AFTER its domain's NRD listing would have no `nrd_domains` row (before the cut every NRD was stored and the hourly lookalike matcher still claimed it). The callers that insert such rows hand the back-check the domains they just inserted: the `lookalike_scanner` agent after its seeder (`seedLookalikesForOrgBrands` → `new_domains`) and BEFORE `runLookalikeNrdMatch`, the manual `POST /api/lookalikes/:brandId/generate` (inline, 10s cap), and the `phantom_enumerator` agent after its inserts. It lists `daily/<date>/` in `NRD_ARCHIVE` for the last 8 UTC dates (`NRD_BACKCHECK_DAYS`, yesterday back), oldest first, stream-gunzips each object, and writes each hit with `upsertNrdBackcheckHits` (`lib/nrd-store.ts`, same EXISTS filter) under the object's date as `registered_date`, `created_at` = now — above both matchers' cursors, so the scanner's match claims it on this run (or the next, if its replica read lags). A hit on a domain ALREADY in `nrd_domains` (a permutation shared across brands — `lookalike_domains` is unique on `(brand_id, domain)`, `nrd_domains` on `domain`) is RE-SURFACED: `created_at` → now, `registered_date` = the earlier of stored vs archive date; re-claiming the first brand is a no-op (`first_seen IS NULL`), the row's retention clock restarts. Results count `stored` and `refreshed` separately; a failed write is reported as `store_errors` + `unstored` (never silent). Bounded: skipped when nothing was seeded or `NRD_ARCHIVE` is unbound, ≤10K domains, 20s soft cap (`timed_out`), and it NEVER throws (per-object errors counted, anything else caught into `error`). A listing older than 8 days is not recovered.
>
> **`nrd_domains` tiered retention (owner decision 2026-10-05).** Three tiers (the table is small now; retention still applies — phantom-only rows age out, and pre-cut rows drain). The lookalike matcher's hold applies only when an unscanned row exists above its cursor (`NRD_RETENTION_UNSCANNED_SQL`, one indexed seek), so a caught-up cursor parked on an old row of the sparse table does not read as `held_by_lookalike_matcher`:
> - **Hot (D1, 30 days).** `lib/nrd-retention.ts` `purgeNrdDomains` deletes rows with `created_at < cutoff AND brand_matched = 0`, where `cutoff = min(now − 30 days, lookalike hold)` (the phantom cursor is clamped at the 30-day cutoff, see Holds). Strict `<`. Chunks seek the partial index `idx_nrd_domains_unmatched_created` (migration 0283, `ON nrd_domains(created_at) WHERE brand_matched = 0`), so kept matched rows are never re-read.
> - **Kept (D1, forever).** Rows with `brand_matched = 1` (set by the NRD ↔ lookalike matcher, `lib/lookalike-nrd-matcher.ts`, on a hit) are never purged. The feed's own brand matches are already permanent in `threats`.
> - **Cold (R2).** Every NEW domain a run processed (flushed — never one deferred by the per-run cap), stored in D1 or not, is gzip-streamed into one object in the `NRD_ARCHIVE` bucket (`averrow-nrd-archive`, top-level binding = prod only) at `daily/<registered_date>/<list version|unversioned>-<first domain>.txt.gz` (`nrdArchiveKey`, prefix `NRD_ARCHIVE_PREFIX`), newline-separated, with customMetadata `{count, stored_in_d1, version, list_modified, registered_date}`. It is the only copy of the NRDs not stored in D1. The put happens once every `nrd_domains` write succeeded — even if threat inserts errored — and BEFORE the diff snapshot advances, so a failed put throws, the snapshot stays, and the next run re-diffs and rewrites the same key (INSERT OR IGNORE keeps D1 idempotent). Threat-insert errors still hold the snapshot, so the retry also rewrites the same key. The first domain in the key keeps a deferral catch-up run on the same list version from overwriting the previous object. Zero new → no object; bootstrap archives nothing. The binding is **required**: unbound `NRD_ARCHIVE` → the pull throws before fetching (retention assumes purged rows are archived). Staging/dev bind neither it nor `GEOIP_STAGING`, so the feed doesn't run there. **Exception:** rows ingested before the archive shipped (2026-10-05) were never archived; once purged they are gone (their brand matches are already in `threats`).
>
> **Holds.** The phantom matcher's nrd cursor (`phantom_matcher:nrd:cursor`, a "scanned up to" watermark that only moves when someone runs the manual matcher incrementally) is clamped AT the 30-day age cutoff, so it never extends retention. A fresher cursor only covers rows the age cutoff keeps anyway; a missing or older one is reported as `phantom_hold_clamped: true`, meaning the rows being purged were never scanned by it. It used to be a hard floor (no cursor → purge nothing), which with a rarely-run manual matcher meant unbounded growth. Effective retention is therefore 30 days in the normal prod state, and `full=1` phantom sweeps cover only that window. The lookalike matcher's keyset cursor (`lookalike_nrd_matcher:cursor`) is a hold only when it exists, clamped to no earlier than now − (30 + 7) days. It binds only when that HOURLY matcher is more than 30 days behind (stuck), extending retention to at most 37 days. A failed or unrecognised cursor READ (either cursor) still purges nothing that run. 5,000 rows per DELETE, 10s soft cap. Runs from Navigator on UTC hour 0 (hour-only gate), once per day, continuing on later hour-0 ticks when a run stops early (`more_remaining`). Manual: `POST /api/internal/nrd-retention/run`. Last result is in KV `nrd_retention:last_result` and surfaced as `nrd_retention` in `/api/internal/platform-diagnostics`: `phantom_hold_clamped`, `held_by_lookalike_matcher`, and `held_by_matcher` (always false on new stamps; kept for shape).

> **Not the same component as `/api/certstream/*`:** a genuinely separate, DO-backed real-time monitor also exists — `CertStreamMonitor` (`durableObjects/CertStreamMonitor.ts`), bound as `CERTSTREAM_MONITOR`, holding a persistent WebSocket to `certstream.calidog.io` and flushing matches to `threats` (`source_feed='certstream'`) every 30s via alarm. It is health-checked every orchestrator tick (`agents/flightControl.ts:1573`, restarts on disconnect) and exposed at `GET /api/certstream/stats` / `POST /api/certstream/reload-brands` (see `docs/API_REFERENCE.md`). It runs independently of `feed_configs`/`feedModules` — it is not part of this registry table, has its own `feed_status` row (`feed_name='certstream'`), and is a distinct feed from the `ct_logs` row above.

## Circuit Breaker Pattern

The feed runner implements a circuit breaker to handle feed failures gracefully. Circuit state is tracked in the `feed_status` table:

### States

- **Closed** (normal) — Feed is healthy, ingestion runs normally
- **Open** (tripped) — Feed has failed repeatedly, ingestion is skipped
- **Half-open** — After cooldown period, one test request is attempted

### Behavior

- Consecutive failures increment a failure counter
- After a configurable threshold (typically 3-5 failures), the circuit opens
- While open, the feed is skipped during cron runs
- After a cooldown period, the circuit moves to half-open
- A successful ingestion in half-open state closes the circuit
- Admin can manually reset a circuit via `POST /api/feeds/:id/reset`

## Safe Domain Filtering

To reduce false positives, the feed pipeline filters threats against a safe domain allowlist. The allowlist is maintained per-brand and stored in the `brand_safe_domains` table.

Safe domain logic is in `packages/averrow-worker/src/lib/safeDomains.ts`. Domains on the allowlist are excluded from brand-threat matching.
